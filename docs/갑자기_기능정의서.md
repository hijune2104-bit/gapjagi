# 갑자기 (Gapjagi) — 기능정의서

> **한 줄 컨셉:** 갑자기 잡힌 일정, 3분 안에 실행 계획으로
> 갑자기 여행·워크샵·회식·회의가 잡혔을 때, 다 같이 의논하고 실행 문서까지 자동으로 뽑아주는 서비스.

| 항목 | 내용 |
|---|---|
| 문서 버전 | v1.0 (프로토타입 기반) |
| 대상 독자 | 개발팀 · 마케팅팀 |
| 기준 산출물 | `gapjagi.html` 인터랙티브 프로토타입 |
| 상태 표기 | ✅ 프로토타입 구현 완료 / 🧪 목업(Mock) / 🔌 실제 연동 필요 |

**이 문서 읽는 법**
- **1~3장(공통)** 은 두 팀이 함께 봅니다. 특히 **3장 기능 카탈로그**의 기능 ID(예: `D-03`, `M-06`)가 개발·마케팅 공통 참조 키입니다.
- **4~7장** 은 개발팀용 상세(화면·데이터·연동)입니다.
- **8장** 은 마케팅팀용(밸류·차별점·메시징·수익모델)입니다.

## 1. 제품 개요

갑자기는 "상황만 고르면 정할 것들을 서비스가 대신 물어보고, 팀이 함께 정한 뒤, 실행 문서(타임라인·예약·공지·알림)까지 자동 생성"하는 모바일 웹 서비스다. 핵심은 세 가지다.

1. **질문을 대신 설계한다** — 빈 채팅창 대신, 무엇을 정해야 할지 서비스가 선택지로 제시한다(탭탭탭 UX).
2. **혼자가 아니라 팀이 정한다** — 링크를 단톡방에 공유하면 팀원이 로그인 없이 투표·응답한다.
3. **결과물이 대화가 아니라 실행 문서다** — 타임라인·예약 정보·회비·공지문·알림이 담긴 실행 가이드가 나온다.

모듈 구조라 상황(회식/회의/여행/워크샵/손님/이사 등)을 무한 확장할 수 있다. 현재 프로토타입은 **회식**과 **회의** 두 모듈이 전체 흐름으로 구현되어 있다.

## 2. 타깃 & 해결하는 문제

| 사용자 | 상황 | 기존의 불편 | 갑자기의 해결 |
|---|---|---|---|
| 모임 주최자 (총무·막내·팀장) | 갑자기 회식/회의를 잡아야 함 | 뭘 정해야 할지부터 막막, 단톡방 핑퐁 | 선택지 기반으로 3분 안에 정리 |
| 일정 조율 담당자 | 5명 회의 시간 잡기 | **안 되는 사람이 반복** → 일일이 재조율 | 반복 불참자 자동 감지 + 원탭 대안 |
| 확정 후 변경 담당자 | 한 명이 갑자기 안 됨 | 전원에게 다시 물어보는 공수 | 대체 시간 자동 탐색 + 전원 일괄 재확인 |
| 팀원(참여자) | 링크로 초대받음 | 앱 설치·로그인 부담 | 로그인 없이 링크에서 탭 응답 |

## 4. [개발] 기능 상세 정의

### 4.1 화면 인벤토리

프로토타입은 클라이언트 상태 머신(`render()` + 화면 함수)으로 구성된다. 화면 목록:

| 구분 | 화면 키 | 이름 | 관련 기능 |
|---|---|---|---|
| 공통 | `home` | 홈(모듈 선택 + 내역 갤러리) | C-01, C-03, C-05 |
| 공통 | `revenue` | 수익 모델 안내 | C-05 |
| 회식 | `d_setup` | 조건 설문 | D-01, D-02 |
| 회식 | `d_pool` | 장소 추천 풀 + 선택 | D-03, D-04, D-05 |
| 회식 | `d_share` | 공유 링크 + OG 미리보기 | D-06 |
| 회식 | `d_guest` | 팀원 수신자(투표) | D-07 |
| 회식 | `d_vote` | 주최자 투표 집계 | D-08 |
| 회식 | `d_result` | 결과·회비·예약 | D-09 |
| 회식 | `d_notice` | 공지문·체크리스트·알림 | D-10, D-11, C-04 |
| 회식 | `t_share` | 진행 내역 공유 | C-03 |
| 회의 | `m_setup` | 가능 시간 입력 | M-01 |
| 회의 | `m_link` | 회의 링크 만들기 | M-02, M-04 |
| 회의 | `m_guest` | 팀원 수신자(가능 시간 응답) | M-03 |
| 회의 | `m_result` | 최적 시간 + 갈등 해결 | M-05, M-06, M-07, M-08 |
| 회의 | `m_propose` | 시간 제안 → 각자 OK | M-09 |
| 회의 | `m_confirm` | 확정 후 후속(준비물·알림·공지) | M-11, M-12, C-04 |
| 회의 | `m_room` | 회의실 예약 | M-10 |
| 회의 | `m_reschedule` | 일정 변경 재조율 | M-13 |
| 회의 | `m_share` | 회의 내역 공유 | M-14 |

### 4.2 회식 플로우 (상세)

```
홈 → d_setup(조건) → d_pool(추천 후보 + 만든 사람 선택)
  ├─ 1곳 선택 → d_result(확정) → d_notice(공지·체크리스트·알림)
  └─ 여러 곳 선택 → d_share(공유/OG) → d_vote(집계) → d_result → d_notice
                        └→ d_guest(팀원 수신자 미리보기)
d_notice → t_share(내역 공유)
```

**핵심 규칙**
- D-04: 후보 1곳 선택 시 CTA는 "이 곳으로 확정", 2곳 이상이면 "팀 투표 붙이기". 결정 주체는 **만든 사람**(별도 결정자 없음).
- D-05: 메모 태그는 후보별로 부여, 팀 투표(`d_vote`)와 수신자 화면(`d_guest`)에 노출.
- D-07: 수신자 화면은 카톡에서 링크를 연 팀원 시점. 게스트(예: "수민")의 투표가 주최자 집계에 실제 반영.
- D-09: 회비 = 예산(1인) × 인원. 결과에 결정 방식 표기("만든 사람이 정함" / "팀 투표 1위").

### 4.3 회의 플로우 (상세)

```
홈 → m_setup(내 가능 시간) → m_link(링크 생성 + OG)
  ├─ m_guest(팀원 수신자: 가능 시간 응답) → m_link 복귀
  └─ "응답 모으고 확정하기" → m_result(최적 시간 + 갈등 해결)
        ├─ 바로 확정 → m_confirm
        └─ 제안 후 각자 OK → m_propose(전원 OK) → m_confirm
m_confirm → m_room(회의실 예약) / m_reschedule(일정 변경) / m_share(내역 공유)
```

**핵심 규칙**
- M-02: `m_setup`에서 주최자가 본인 가능 시간을 칠하고 "회의 링크 만들기" → 응답자 집합 `responded = {나}` 로 시작.
- M-03: 수신자(`m_guest`)가 가능 시간을 제출하면 `responded`에 추가되고, 그 응답이 집계에 반영.
- M-06/M-07: 상위 3개 시간대에 0번 가능한 사람을 **반복 불참자(blocker)** 로 감지. "빼고 확정"은 해당 인원 제외 후 최적 시간으로 즉시 확정, "전원 되는 시간 찾기"는 전원 가능 슬롯 탐색(없으면 개별 조율 안내).
- M-10: `m_confirm`에서 회의실 카드 → `m_room` 진입. 인원 수용 가능한 가장 작은 방 추천, 사용중/인원초과 방은 선택 불가. 예약 완료 시 공지에 반영.
- M-13: 확정 후 한 명이 안 될 때, 현재 시간을 제외한 대체 시간을 점수순 3개 제시 → 선택 시 `m_propose`로 이동해 **전원에게 일괄 재확인**. 새 시간은 회의실 재예약 유도.

### 4.4 상태(데이터) 모델

프로토타입 클라이언트 상태 기준. 실제 구현 시 서버 스키마의 기준으로 활용.

**회식 `S.dinner`**
| 필드 | 타입 | 설명 |
|---|---|---|
| date, region, people, budget, food, vibe | string | 설문 선택값 |
| shortlist | string[] | 만든 사람이 고른 후보 id |
| comments | { [id]: string[] } | 후보별 메모 태그 |
| votes | { [id]: {n,c}[] } | 후보별 투표자 목록 |
| myVote / guestVote | string | 주최자 / 게스트 선택 후보 id |
| winnerId | string | 직접 확정 시 승자 id |
| decidedBy | 'creator' \| 'vote' | 결정 방식 |

**회의 `S.meeting`**
| 필드 | 타입 | 설명 |
|---|---|---|
| mine | Set | 주최자 가능 시간 슬롯(`요일-시`) |
| responded | Set | 응답 완료한 참여자 이름 |
| guestAv | Set | 수신자(게스트) 응답 슬롯 |
| exclude | string[] | 제외된 참여자 |
| confirmed | {slot,cnt,n} | 확정 시간·가능인원·총원 |
| proposed | {slot,cnt,reason} | 제안/재확인 시간(사유 포함) |
| oks | Set | OK한 참여자 |
| roomId / roomBooked | string / bool | 회의실·예약 여부 |
| prep | Set | 준비물·아젠다 |
| alerts | Set | 예약된 알림 종류 |
| changer | string | 일정 변경이 필요한 팀원 |

### 4.5 슬롯/집계 로직 (회의)

- 슬롯 키: `"{요일}-{시}"` (예: `수-15`).
- 점수: 각 슬롯에서 `가능한 응답자 수`.
- 최적 시간: 점수 최댓값 슬롯.
- 반복 불참자: 상위 3개 슬롯 중 가능 횟수 0인 사람.
- 대체 시간(재조율): 현재 확정 슬롯 제외, 점수순 상위 3개.

## 6. [개발] 비기능 요구사항 (권장)

- **무설치/무로그인 참여:** 링크 진입 + 닉네임만으로 투표·응답. 세션은 짧은 고유 ID(`/s/{id}`, `/m/{id}`).
- **모바일 우선:** 단톡방 공유 → 모바일에서 열림 전제. 반응형 필수.
- **실시간성:** 해커톤/초기엔 3~5초 폴링으로 충분, 확장 시 WebSocket.
- **OG SSR:** 크롤러는 JS 미실행 → 메타 태그는 서버사이드 렌더로 제공.
- **접근성/모션:** `prefers-reduced-motion` 존중(프로토타입 반영됨).
- **추천 폰트:** Pretendard(+시스템 한글 폴백).

## 7. [개발] 예외/엣지 케이스

- **전원 되는 시간 없음(M-07):** "전원 되는 시간이 없어요 — 개별 조율 필요" 안내.
- **응답 미완료 상태에서 결과 진입(M-04):** 응답한 사람 기준으로만 최적 시간 계산.
- **일정 변경 후 회의실(M-13):** 시간 변경 시 회의실 예약 상태 리셋 → 재예약 유도.
- **제휴 식당 투명성(D-12):** 광고는 항상 'AD·제휴' 배지 + 하단 고지. 순위 조작 아님(투표는 팀 자유).
- **미성년/부적절 상황:** 해당 서비스 범위 아님(성인 팀 모임 전제).

## 8. [마케팅] 포지셔닝 & 메시징

### 8.1 밸류 프로포지션

> **"갑자기 잡힌 일정, 3분 안에 실행 계획으로."**
> 정하기 귀찮은 회식·회의를, 물어보는 것부터 확정·공지·알림까지 대신 해주는 팀 실행 도구.

### 8.2 핵심 차별점 (vs ChatGPT·설문·단톡방)

| # | 차별점 | 근거 기능 |
|---|---|---|
| 1 | **질문을 대신 설계** — 빈 입력창이 아니라 탭탭탭 선택지 | D-01, M-01 |
| 2 | **혼자가 아니라 팀 합의** — 링크로 모두 투표/응답 | D-07, M-03 |
| 3 | **대화가 아니라 실행 문서** — 공지·회비·예약·알림 결과물 | D-09, D-10, M-12 |
| 4 | **조율 공수 제거** — 반복 불참자·확정 후 변경을 원탭 처리 | M-06, M-07, M-13 |

### 8.3 페인포인트 → 후크 메시지

| 페인포인트 | 마케팅 후크 | 기능 |
|---|---|---|
| "회의 시간 잡다가 하루 다 감" | 안 되는 사람이 반복돼도 탭 한 번으로 정리 | M-06/M-07 |
| "확정했는데 한 명이 못 온대…" | 일일이 다시 안 물어봐도, 전원에게 한 번에 재확인 | M-13 |
| "어디서 먹지? 룸 되나?" | 조건만 고르면 후보 추천, 룸 여부까지 표시 | D-03/D-05 |
| "매번 처음부터 정하기 귀찮아" | 잘 된 회식 세팅을 배경화면처럼 공유·재사용 | C-03 |

### 8.4 타깃 & 사용 맥락

- **1차 타깃:** 회사 팀 단위(주최자 = 총무·막내·팀장), 오피스 밀집 권역.
- **참여자 경험:** 앱 설치·로그인 없이 카톡 링크에서 바로 응답 → 진입 장벽 최소.
- **바이럴 루프:** 한 사람의 진행 내역이 다음 팀의 시작점이 되는 **내역 공유(C-03)** = 자연 확산.

### 8.5 수익 모델 (C-05, D-12)

1. **권역별 상단 노출 슬롯** — 식당이 자기 권역 후보 상단 자리를 구매('AD' 명시).
2. **예약 전환 수수료** — 확정·예약 발생 시 건당 수수료.
3. **지역 수요 데이터** — "성수권·10인·고기" 같은 실수요 리포트 제공.

> 투명성 원칙: 제휴는 항상 광고로 명시하고 투표/선택은 팀 자유. 신뢰가 곧 전환율.

### 8.6 확장 로드맵 (메시지용)

- **모듈 확장:** 여행·워크샵(예정) → 손님·이사 등 무한 확장.
- **애드온 SKU 후보:** 'AI Guard'(민감정보 차단)·'Mail Safe' 등 프리미엄 계층 (별도 검토).
